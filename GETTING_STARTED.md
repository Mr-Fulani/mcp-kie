# Установка и применение со своими ключами

Это инструкция для новой локальной установки Secure KIE MCP. Используйте собственный
аккаунт KIE и собственный media key. Отчёты `audit/` описывают историческую проверку
на другом компьютере; копировать оттуда пути, ключи или настройки аккаунта не нужно.

## 1. Подготовить окружение

Нужны Python 3.11+, [uv](https://docs.astral.sh/uv/getting-started/installation/),
Git и MCP-клиент с поддержкой локального stdio. Поддерживаются macOS и Linux.
На Windows используйте WSL2: репозиторий, виртуальное окружение, ключ и рабочие папки
должны находиться в Linux-файловой системе (`~/...`, не `/mnt/c/...`). MCP-клиент
запускайте в том же Linux-окружении: автоматическое подключение нативного Windows
клиента через `wsl.exe` не реализовано. Нативная Windows
не поддерживается; отдельная реальная приёмка WSL2 пока не проведена.

Наш самостоятельный репозиторий — [Mr-Fulani/mcp-kie](https://github.com/Mr-Fulani/mcp-kie).
Исходный пример указан только в NOTICE для сохранения MIT attribution.

```sh
git clone https://github.com/Mr-Fulani/mcp-kie.git
cd mcp-kie
uv sync --frozen
```

`--frozen` использует `uv.lock`. Не запускайте обновление зависимостей для обычной
установки. Не меняйте DNS/endpoint/проверки TLS, чтобы обойти ошибку сети.

## 2. Создать собственный ключ и выбрать лимиты

В своём аккаунте KIE создайте отдельный ключ для медиа. Не используйте ключ своего
chat/coding provider. OpenAI/Anthropic/chat KIE ключи MCP-серверу не нужны: вход в
Codex/Claude/Grok — отдельная задача самого клиента.

Проверьте доступные ограничения расходов/моделей на стороне KIE. Локальные лимиты
MCP основаны на консервативном расчёте и не гарантируют, что провайдер не спишет больше
своей заявленной цены. Перед unattended-работой подтвердите provider-side caps.
Если провайдер не даёт нужного ограничения, не считайте локальный лимит абсолютной
гарантией расходов.

По умолчанию лимиты: $1 на задачу, $5 на MCP-процесс/сессию, $10 на UTC-день,
$100 суммарно, пять одновременно зарезервированных/активных задач. Задайте свои
значения **до первой платной операции**. Все процессы должны пользоваться одним
ledger и одинаковой сохранённой политикой. Новый путь ledger не является способом
«сбросить» расход; изменение политики существующей БД требует отдельной сверки.

## 3. Папки и конфигурация владельца

Для новой установки создайте отдельные папки вне репозитория:

```sh
mkdir -p ~/.config/kie-mcp ~/.local/share/kie-mcp ~/kie-workspace/uploads ~/kie-workspace/results
chmod 700 ~/.config/kie-mcp ~/.local/share/kie-mcp ~/kie-workspace/uploads ~/kie-workspace/results
```

Не назначайте uploads на весь домашний каталог, корень диска, репозиторий с секретами
или папку ledger. Uploads и results должны быть раздельными и не вложенными друг
в друга. В uploads вручную кладите только файлы, которые действительно хотите
передать провайдеру.

Откройте `examples/owner-config.toml` (macOS) или
`examples/owner-config-linux.toml` (Linux/WSL2). Проверьте пути, источник секрета и
лимиты. Сохраните свою копию как `~/.config/kie-mcp/config.toml`, затем:

```sh
chmod 600 ~/.config/kie-mcp/config.toml
```

В TOML разрешён только раздел `[environment]` с поддержанными именами. Ключ туда
**не записывается**. Пути должны быть абсолютными или начинаться с `~`; относительные
пути отклоняются, поскольку MCP-клиенты могут запускать сервер из разных папок.
Если конфигурация уже существует, не перезаписывайте её примером. При необходимости
сам владелец задаёт другой абсолютный путь через `KIE_OWNER_CONFIG` в окружении
запуска клиента. Явно указанный отсутствующий файл вызывает ошибку.

## 4. Сохранить секрет отдельно

### macOS: Keychain

В интерфейсе Keychain Access создайте generic-password item:

- service/name: `kie-mcp-media`;
- account: `media`;
- password: ваш отдельный media key.

Пример macOS использует `KIE_SECRET_SOURCE="macos_keychain"`. При первом обращении
Keychain может запросить доступ. Не передавайте ключ в аргументах `security`, не
публикуйте его в shell profile, JSON клиента или чате. Если у вас другие labels,
владелец меняет только `KIE_KEYCHAIN_SERVICE`/`KIE_KEYCHAIN_ACCOUNT` в своём TOML.

### Linux/WSL2: приватный файл

Пример Linux задаёт `KIE_SECRET_SOURCE="secret_file"` и
`KIE_SECRET_FILE="~/.config/kie-mcp/media.key"`. Для **нового** файла создайте пустой
файл с приватными правами; команда откажется затирать существующий файл:

```sh
(umask 077; set -C; : > ~/.config/kie-mcp/media.key)
```

Откройте его локальным редактором и вставьте только media key одной строкой.
Проверьте после сохранения:

```sh
chmod 600 ~/.config/kie-mcp/media.key
```

Не вставляйте ключ в терминальную команду, Git, чат или конфигурацию MCP-клиента.
Это обычный **незашифрованный файл**: нужны защита каталога/диска и доверенный OS user.
Файл должен принадлежать запускающему пользователю, быть regular file, не симлинком,
с правами 0600 или 0400 и размером не более 16 KiB. Финальный симлинк/FIFO/device
отклоняется. Владельцу нужно защитить также родительские каталоги.

В Docker поддержан фиксированный secret mount `/run/secrets/KIE_MCP_API_KEY` и
`KIE_SECRET_SOURCE="docker_secret"`. Готового образа/Compose/hard sandbox в репозитории
нет; container deployment нужно спроектировать отдельно. `env` оставлен для dev/tests;
`.env.example` описывает переменные, но `.env` автоматически не читается.

## 5. Проверить установку без сети и оплат

```sh
.venv/bin/kie-mcp-doctor
.venv/bin/kie-mcp-doctor --check-secret
```

Доступен и `.venv/bin/python -m kie_mcp.doctor`; `--json` выдаёт структурированный
отчёт без значений конфигурации/ключа. Код выхода 1 означает FAIL, 0 — отсутствие
FAIL; WARN требует внимания, но не всегда блокирует запуск.

Doctor проверяет платформу, TOML, числа/пути, папки и размещение ledger/секретов.
Он не меняет настройки, не создаёт ledger, не отправляет запросы, не проверяет
provider-side caps и совместимость сохранённой политики в существующей БД. Обычно
он не читает ключ. `--check-secret` только проверяет загрузку, никогда не выводит
значение и не проверяет его валидность у KIE. Для проверки авторизации потребуется
read-only MCP-вызов `kie_get_credits` после подключения клиента.

## 6. Подключить MCP-клиент

Из корня checkout выполните preview для нужного клиента:

```sh
.venv/bin/kie-mcp-register codex --command "$PWD/.venv/bin/kie-mcp-launch"
```

Вместо `codex` можно выбрать `claude` или `grok`. Проверьте имя и абсолютный путь,
после чего примените:

```sh
.venv/bin/kie-mcp-register codex --command "$PWD/.venv/bin/kie-mcp-launch" --apply
```

Registrar меняет только отдельную регистрацию `kie-media`, создаёт приватный backup,
сохраняет остальные настройки и отказывает при несовпадающей существующей записи.
Не запускайте его одновременно с другими редакторами конфигурации клиента.

Для другого stdio-клиента задайте command = абсолютный путь `kie-mcp-launch`,
args = пустой список. Ключа в записи не должно быть. Запуск launcher в обычном
терминале сам по себе не показывает меню: процесс ожидает протокол MCP по stdio.

Перезапустите клиент. Проверьте инструменты: 23 tools, включая `kie_compare_models`.
Добавьте правила из [examples/AGENT_INSTRUCTIONS.md](examples/AGENT_INSTRUCTIONS.md)
в проектные инструкции своего агента. Копия инструкции дополняет защиту кода,
но не создаёт OS-изоляцию. Вызовите `kie_get_credits`: это проверка авторизации/баланса,
без генерации и резервирования. Полный ключ в результате не должен появляться.

## 7. Первая задача: сравнение → выбор → preview

Попросите агента: «Через Secure KIE MCP сравни модели для студийного фото товара.
Покажи доступные параметры и цену. Дождись моего выбора перед подготовкой задачи».

Без `model` friendly-команда возвращает список выбора. Тарифы/схемы/каталог каждый
раз запрашиваются у KIE; если обязательные данные недоступны, старый список не
подставляется. Наличие модели не гарантирует её работоспособность. По умолчанию
пять кандидатов; `kie_compare_models` поддерживает query, cursor/next_cursor и
до десяти моделей на страницу. Несовместимые варианты отображаются с причиной.
Цена относится к конкретным запрошенным/default параметрам; описания качества —
заявления провайдера. Независимые оценки качества/скорости не реализованы.

После выбора модели агент вызывает friendly-команду с `model` и `dry_run=true`.
Сравнение не загружает фото; exact preview локального/внешнего фото **может загрузить
его в KIE**. Для дополнительных объявленных полей есть `model_input`.
Неизвестная цена не равна нулю: используйте поддержанный тариф или частную exact-input
котировку, которую проверяет и записывает сам владелец. См. [PRICE_SUPPORT.md](PRICE_SUPPORT.md)
и `examples/owner-quote.json`. Не разрешайте агенту самостоятельно одобрять quote.

Затем проверьте запрос/цену, разрешите подготовку и одну платную отправку:

1. `kie_prepare_task` с preview `request_payload.model/input`: резервирует бюджет.
2. `kie_execute_task` с `approval_id` и неизменёнными model/input в той же сессии:
   заново проверяет schema/price и отправляет одну задачу.
3. `kie_wait_for_task`/`kie_get_task`: дождаться terminal success/fail.
4. `kie_download_result` для success: сохранить фактический результат в results.

Preview payload нужно сохранить неизменным, включая уже загруженный URL. Не
вызывайте повторно friendly preparation лишь для исполнения: это может повторно
загрузить изображение или поменять запрос. `auto_select=true` допустим при явном
поручении выбрать самый дешёвый вариант: scope — первые 20 кандидатов с известной
ценой, без оценки качества/health. Сложные схемы требуют low-level input.

## 8. Сохранение, обновление и устранение ошибок

Новые сохранения используют папки дата/короткое название/тип/модель/полный task ID.
`result_label="студийное фото"` необязателен и допускает до 48 UTF-8 байт, буквы,
цифры, пробелы, дефисы и подчёркивания. Старые папки не переименовываются; фактические
байты определяют формат/расширение. Вернувшиеся output_path/output_folder указывают,
где искать файл. KIE URL временные — скачивайте важные результаты своевременно.

| Ситуация | Что делать |
|---|---|
| Secret/config missing | Doctor; проверить источник, абсолютный путь, owner и права. Не печатать ключ для диагностики |
| Авторизация KIE не работает | В своём аккаунте проверить media key/доступ; не подменять его chat key |
| Unknown price | Выбрать reviewed параметры/модель или подготовить owner quote; не угадывать USD/credit rate |
| Поменялась цена/schema/digest | Новый preview и осознанная подготовка; не менять уже одобренный запрос |
| Shared policy mismatch | Сверить все процессы/ledger и политику владельца; не удалять БД |
| Таймаут/5xx после отправки | Сохранить liability/task ID; проверить историю KIE перед любой повторной отправкой |
| Provider fail | Проверить credits/refund/state; не считать автоматически, что оплаты не было |
| 429 metadata | Выполнять сравнение последовательно; общий limiter между несколькими процессами не реализован |
| URL/file rejected | Использовать разрешённые корни и secure upload; не отключать SSRF/проверки путей |
| Клиент не видит новые tools | Перезапустить MCP-клиент после обновления |

Для обновления сначала завершите/сверьте активные задачи, ознакомьтесь с diff,
обновите checkout до нужной ревизии и выполните `uv sync --frozen`. Не запускайте
параллельные копии с разными бюджетами/ledger. Не копируйте примеры поверх своей
конфигурации и не удаляйте ключи/ledger/results при обновлении.

Удаление только регистрации: повторите команду registrar с тем же client/command
и `--remove --apply`. Она не удаляет ключи, ledger, конфиги владельца или медиа.

Полная граница защиты: [SECURITY.md](SECURITY.md). Агент с shell/network доступом под
тем же OS user находится вне этой границы. Для недоверенного агента нужна отдельная
OS/container изоляция; инструкция и plaintext secret file её не заменяют.

Готовые запросы и таблица команд: [CHEATSHEET.md](CHEATSHEET.md).
